# E4 旧版隔离与恢复

实测环境为 Windows，使用已发布的 `0.1.7-beta.2` 便携包和一个经 E3 验证的真实 Schema v19 项目。便携压缩包 SHA-256 为 `cc8e63b7f6803cbad94d43ff7e1be5e83adb2b15afc61c5040ab9d5de217ca66`，与发布资产一致。用独立应用配置和 Chromium 数据目录启动打包应用，通过其生产 preload 调用项目打开、最近项目和草稿读取入口。[发布资产](https://github.com/LunaRime/novelforge/releases/tag/v0.1.7-beta.2)

## 旧版打开验证

从同一份旧项目制作两个对照目录。文件正文包含一处仅用于验证的新编辑，冻结快照的旧正文可通过哈希区分。

| 场景 | Windows 打包应用实测 |
|---|---|
| 新章节文件与旧 SQLite 库位于同一项目，`novel.json` 有存储标记 | 旧版成功打开，草稿读取返回旧 SQLite 正文。 |
| 文件项目位于独立目录，旧 SQLite 路径 `.novelforge/vela.db` 由空目录占用 | 旧版打开失败，最近项目列表没有新增该项目。空目录及文件项目内容保留，当前文件仓储可重新打开并读取新正文。 |
| 直接打开隔离保存的完整项目 ZIP | 旧版打开失败，最近项目列表没有新增压缩包，压缩包 SHA-256 保持一致。 |
| 把 ZIP 解包到新的恢复目录，再用匹配版本打开并重启 | 解包后 44 个文件的 SHA-256 与快照一致。旧版两次打开均按 ID 读回 14 条原草稿，正文哈希一致。恢复库保持 Schema v19 并通过 SQLite 完整性检查。 |

原项目的文件 SHA-256 前后一致。带新编辑的文件项目和恢复副本保留在各自目录，真实路径、项目数据、快照及完整验收报告在仓库外保存。

## 后续切换采用的隔离条件

1. 把迁移前的完整项目快照保存成归档文件，放在旧版项目根之外，记录匹配应用版本、Schema、归档哈希和快照时间。曾被旧版登记的原目录仍代表切换前状态，文件项目使用独立目录与入口。
2. 文件项目发布前保留 `.novelforge/vela.db` 目录作为旧版数据库打开屏障。入口核对该目录存在，且没有可被旧版选中的 SQLite 文件或旧目录回退路径。需要保留的应用数据库使用另一个路径。项目打开测试需覆盖目录缺失、同名普通文件与符号链接。
3. 用旧版回退时，先从文件项目另行保全切换后新增的稿件。核验归档哈希，在新目录恢复完整快照，用与快照匹配的版本打开，再核对草稿和关联。回退结果对应归档时间点。

本次验证覆盖 Windows 上的指定旧版、离线文件仓储和真实备份恢复。F 批次仍需在实际发布与打开入口验证隔离条件、故障恢复和接入后的应用生命周期。[后续实施计划](18-followup-implementation-plan.md)
