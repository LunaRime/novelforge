# 第一部分 · 自审报告

按严重度排序。P0 会丢数据或卡死用户，必须在动手前修掉。

## P0-1：删表方案对存量用户不可逆

**原文**（06 第十节）：「删 `contents` / `draft_snapshots`（先备份成 `.db.bak`）」。

**问题**：这是把「重构」当「绿地」写。15 个用户的章节正文全在 `contents.body`，删表即不可回退；用户装回 0.1.7 会直接 `no such table`。

**违反**项目明文规范（`db-migration-standard` 第一条）：

> 幂等性（最高优先级）。每一步迁移必须可安全重复执行。
> **真实事故**：v6 step 10 删除列 premis → step 6 下次启动 SELECT premis → `no such column` → 迁移死循环。

**修正**：`contents` / `draft_snapshots` **不删**，只标记 deprecated，至少保留两个大版本。删除是最后一步，且只在「确认无回退用户」后才执行。

## P0-2：没有降级闸门

**原文**：整份方案假设「迁移后用户只往前走」。

**问题**：用户装了 0.2，数据迁成文件；他重装回 0.1.7，旧版只认 DB，会看到**冻结的旧状态**——最近的章节「凭空消失」。这是最容易被投诉成「你们把我稿子弄丢了」的场景。

**修正**：区分两个版本号，并把「降级检测」写进启动路径：

```ts
// user_version 管 schema，storage_version 管存储形态，两者独立
const STORAGE_VERSION = 1;   // 0=纯 DB  1=双写  2=文件为真相

if (db.prepare('SELECT v FROM storage_meta').get()?.v > SUPPORTED_STORAGE_VERSION) {
  // 旧版看到新库：不静默建空库，不跑迁移，明确拒绝并给出手动恢复指引
  throw new StorageTooNewError(projectPath);
}
```

## P0-3：双写失败会静默丢稿

**原文**（06 4.1）：`save()` 只做「原子写 + 更新索引」，没有错误反馈。

**问题**：违反 `save-feedback-standard`——那个规范正是从真实事故来的：

> `DraftEditor` 保存失败静默（无 catch）、`CharacterEditor` 抛错冒泡、模型配置保存无反馈——用户点击保存无任何视觉反馈。

文件写入比 DB 更容易失败（磁盘满、杀软锁文件、路径过长、只读目录）。**双写阶段最危险的失败模式是：DB 写成功、文件写失败，用户以为存了，重启后回退到旧内容。**

**修正**：保存点必须补齐三件套（日志 + toast + 错误处理），并额外记录 `shadow_write_fail` 事件；连续失败 3 次自动降级为「只写 DB」并提示用户。

## P1-1：没复用项目已有的迁移基建

项目里已经有三套成熟的迁移先例，我的文档一个都没引用：

| 已有实现 | 位置 | 可复用点 |
|---|---|---|
| `safeAddColumn(db, table, col, def)` | `electron/database.ts:682` | 加列必须走它，禁止裸 `ALTER` |
| `migrateExistingTables(db)` | `electron/database.ts:699` | 补列/补约束的既有范式 |
| `migrateLegacyDirs()` | `electron/main.ts:324` | **哨兵文件判定 + 失败静默 + 旧路径兜底读取** |
| `runCredentialMigration()` | `electron/main.ts:332` | 幂等 + 首次执行前留 `.pre-credentials.bak`（`main.ts` 注释：失败不阻断启动） |

`migrateLegacyDirs` 的哨兵模式恰好能解决 P0-2：用「新目录存在 + config.json 哨兵」判断是否迁移过，而不是只看版本号。

## P1-2：漏了 `.novelforge/` 未被 gitignore 这个事实

已逐行核对：`.gitignore` 有 `node_modules`/`dist`/`logs`/`.agents/` 等约 20 组条目，**但没有 `.novelforge`**。所以 **`.novelforge/vela.db` 会被提交**。

后果（仅在用户于项目目录跑过 `git init` 时成立，但这类用户不少）：

- 用户仓库里躺着二进制 db，迁移后会新增 `chapters/*.md`，两者并存，diff 噪音翻倍
- 「文件方案对 git 友好」这个卖点，要等用户意识到 db 也可以移出版本库才成立
- **我们不能替用户改 `.gitignore`**（那是他的仓库），只能在应用内提示 + `doctor` 里列一条检查项

## P1-3：把估算写成了结论

06 写「1000 章 rescan < 1s」——这是按每章几 KB 推算的，**没有压测**，不该以结论口吻写进方案。真实数字要等原型压测，或直接用 `doctor` 在用户的真实项目上量。

> 更正一处我自己的误记：写这份审阅时我称「06/01 写 22 张表」，实际核对后文档里没有这个表述，现状图里 db 节点标的是 23 张（已与代码核对一致）。审阅报告本身也不该带未经核实的指控。

## P1-4：把「运行时伪造字段」当成「DB 列」讨论

06 说「删 `DraftMeta.filePath` / `fileName` 要迁移」。实际上它们是 `src/services/draft-index.ts` 里 **TS 接口的字段**，运行时拼出来的，DB 里没有这两列。

删它们不涉及任何数据迁移，只涉及 UI 改动——**这件事的性质比文档描述的轻，但 UI 改动面比描述的广**。

## P2-1：只迁章节，设定/角色仍留在 DB

06 的目录结构画了 `setting/characters/*.json`，但迁移路径只写了章节。第一版应该明确：**只迁章节正文，设定/角色/大纲先留 DB**，避免一次动太多。

## P2-2：新增文案没走 i18n

所有迁移提示（「已升级项目格式」「请勿回退版本」）必须走 `t()`，三语覆盖。这是 `AGENTS.md` 的硬约束，文档里一句没提。

## 小结

| 级别 | 数量 | 影响 |
|---|---|---|
| P0 | 3 | 会丢稿 / 卡死用户 |
| P1 | 4 | 返工、误导 |
| P2 | 2 | 规范 |

# 第二部分 · 当前离线迁移与后续切换条件

## 一、当前交付边界

本轮实现独立存储核心与迁移工具，应用的 Electron、UI、agent 保存与读取入口仍使用现有 DB。工具不是应用升级钩子，不在打开项目时自动执行，也不更改原项目的 storage_version、schema 或任何业务行。

原阶段 A 影子写入、阶段 B 双写和阶段 C 剪断方案撤销。不能把本文历史片段中的 SQL 或按章号生成 id 的样例直接用于迁移。

## 二、安全离线导出

1. 使用原库的一致性只读快照；输出到与原项目隔离的新目录。已有非空目录必须拒绝，不能清空或覆盖它。
2. 枚举章节和历史版本，保留来源标识。迁移章节 id 按 04 附录 B 的确定性规则生成；同章版本共享章节身份，不能按每个版本各建一个章节。
3. 章节文件使用 chapters/{4位序号}.md，标题仅在 frontmatter；序号或 id 冲突直接失败，不能覆盖另一章。
4. 校验每章正文 hash、章节数、版本映射与历史内容。任何不一致都视为未完成，不写成功标记；原 DB 保持可继续使用。
5. 完整性验证后，才在输出目录生成迁移清单与来源版本。重跑输出目录不得被当成一次新的空目录迁移；使用新的空目录比较结果，或在后续提供具备完整核验的幂等恢复协议。
6. 失败返回可诊断错误和非零退出码，保留输出以供检查。工具不删除原数据，不自动清理失败目录。

doctor 与契约验证应覆盖：删派生索引后重建、外部改名与编辑、重复 id、编号冲突、临时文件、跨项目边界、正文及历史 hash 对照。原型仅验证文件语义，不能替代真实库副本上的导出验收。

## 三、storage_version 的实际作用

storage_version 只能约束实现了检查逻辑的版本。已发布的 0.1.x 不认识 storage_meta，增加这张表不会使旧版抛出 StorageTooNewError，也不能阻止旧版继续写旧 DB。

当前因此采用隔离输出，应用仍开原项目。未来切换必须单独落实新旧项目识别、备份恢复、用户提示和回退规则，不能把版本表当成旧版隔离机制。user_version 只管理 DB schema，不能伪装成存储格式闸门。

## 四、后续应用切换的准入条件

- 实际项目库副本完成导出、完整性报告和恢复演练，所有契约通过。
- 明确切换后文件是真相，旧库冻结；所有 UI 与 agent 写入口统一接入文件存储后再启用。
- 文件保存失败必须日志、用户反馈、错误返回齐全；禁止回退只写 DB 或报告成功，否则下一次文件读取会回退旧稿。
- 设置、角色、大纲第一版继续留 DB。schema 改动遵守 safeAddColumn、幂等与原子版本递增要求。
- 提示与保存反馈走 t() 三语。任何切换操作须有独立验收记录；本轮完成核心和迁移测试不代表应用已经迁移。

## 五、用户数据保护

原 DB 与备份始终保留；不自动删旧表。未来文件真相启用后，回退应用必须同时恢复匹配的数据快照，不能直接打开冻结旧库当作最新稿。导出清单应说明来源、目标、章节及历史数、校验结果和工具版本。
