# 修稿合并用例与原子提交（2026-11-06）

基线：`d3c7b3e`，分支 `codex/revision-merge-application`。接续 15 号编辑器抽离批次，将 draft-store 中的合并业务移到应用用例。

## 现状与目标

原 `applyMergedRevision` 在 renderer 校验后依次更新正文、草稿状态、修稿标记。三个 IPC 不是同一事务；既有正文单次 CAS 不能保证整次合并的原子性。因此不能把上一批复用旧 store 的实现表述为“合并三项已原子提交”。

本批让正文、revised 状态、merged 修稿标记和相关快照一起提交或回滚。DB 仍是事实源，UI/store 只在成功后刷新投影，用户未保存内容与 inline 会话继续保留。

## 边界

不迁移、不冻结、不删用户表，不改 schema/版本/已有 URI。其他保存通道继续保留给各自调用者。新合并命令不能使用章号猜身份，不能以一次内容写入成功代表整次合并成功。UI 继续负责确认和反馈，临时测试/构建日志统一写入 `logs/tmp/`。

UI 的初始正文必须来自打开合并界面时的源快照；缺少快照应拒绝提交，而不是临时重读新正文后绕过冲突。提交成功之后的缓存和目录刷新属于投影阶段，须与持久化结果区分。
