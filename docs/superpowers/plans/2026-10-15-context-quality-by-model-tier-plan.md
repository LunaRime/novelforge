> **状态**：**计划稿（未实施，待拍板）**——只写目标、判据、改法与验收，不含已落地代码。
> **日期**：2026-10-15 ｜ **行号基线**：master `52a4972`（附录 B 评审修复已入库并推送，CI 三平台绿）
> **目标重述（用户拍板口径）**：**让好模型发挥它原有的性能；让差模型在此基础上再上一层。**
> **依据**：`2026-10-14-agent-context-hardening-plan.md`（含附录 A 实测 / 附录 B 修复）、`2026-10-15-self-learning-compression-design.md`、本仓实测数据（工具契约 3612 tokens、base 2150→4577、启发式/tiktoken ≈ 1.68×）

## 0. 为什么把目标写成这两句

"提升小说生成质量"太模糊，会被"加更多提示词 / 换更强模型"这类无判据的动作填满。拆成两条可判定的轨道后，每个工作项都必须回答它在哪条轨道上、以及拿什么数字证明：

| 轨道 | 一句话判据 | 反面（本轨道要消灭的） |
|---|---|---|
| **S：不拖累强模型** | 强模型在**没有本系统**时的能力上限，不因上下文层而下降 | 工具契约读不全、任务状态被压进摘要、token 口径错导致过早压缩 |
| **W：抬高弱模型** | 弱模型的**下限**被抬高：更少跑偏、更少过早收尾、更少"忘了前面说过什么" | 把弱模型当强模型用：给一堆压缩摘要让它自己脑补 |

**关键不对称（本计划的设计前提）**：同一个机制在两轨上收益不同甚至相反——
- **精简/压缩**对强模型几乎无损（它能从摘要重建），对弱模型是**灾难**（它不能）；
- **结构化指令/工具契约/自检提示**对强模型是噪音，对弱模型是**脚手架**。
所以"统一调优"是错的方向，正确方向是**按模型档位分层**（§2 W1）。

## 1. 非目标

1. 不训练/不微调模型，不引入 LLM-as-judge 自动回滚（成本随轮次线性上升、判据不稳）。
2. **不用测试钉住 fallback token 口径**（见 §3 S1：余量太薄，任何新工具都会让它假红）。
3. 不给强模型堆更多规则/提示——强模型需要的是**干净的上下文**，不是更多指令。
4. 不按 `modelName` 硬编码白名单：只用已有客观信号（`ModelProfile.contextWindow` + 路由档位）。
5. 不改"原文永不删""只影响之后的压缩"两条既有契约。

## 2. 现状盘点：哪些机制在拖累，哪些在抬升

| 机制 | 现状 | 对 S（强模型） | 对 W（弱模型） |
|---|---|---|---|
| 工具契约 3612 tokens 全量可读（附录 B P0-3） | 已修 | ✅ 契约完整 | ✅✅ 弱模型最吃这条（它不会靠常识补参数语义） |
| 分节摘要 + 注入端分节裁剪（P1-1） | 已修 | ✅ 尾部任务/决策不再被砍 | ✅✅ 固定分节 = 可预期的结构 |
| 保真检查（P1-2） | 已修 | ✅ 丢实体有告警 | ✅ 告警同时是学习信号 |
| **token 口径 fallback**（`gpt-tokenizer` 失败 → 启发式） | 局限：失败只 `console.warn`；中文高估 ≈1.68× | ❌ 长上下文能力被浪费：压缩提前 ~40% 触发 | ❌ 压缩更碎 → 摘要更多、每批更短 → 漂移概率上升 |
| **任务状态没有免压缩保护** | 缺口：压缩批从最旧累积（`archive-codec.ts:99`），进行中的任务可能被压进 250-token 摘要 | ⚠️ 多步任务丢细节 | ❌❌ 直接跑偏/过早收尾 |
| **预算全是全局常量**（`budgetPercent` 80 / 工具 4000 / M1 300 / L1 600） | 缺口：与"谁在跑"无关 | ⚠️ 长窗口模型被按 80% 压（本该 90%） | ❌ 弱模型拿到与强模型同样长的上下文（对它是干扰） |
| 记忆取用靠 `@` 硬门控 + `read_memory` 工具 | 缺口：弱模型不会主动 @ / 不会主动查 | ✅ 强模型自取 | ❌ 写了记忆却用不上 |
| 未完成自检 | 缺口：模型"自认为完成"时无提示 | ✅ 强模型自己会检查 | ❌ 弱模型过早收尾 |

## 3. 工作项

### 轨道 S（不拖累强模型）

#### S1 token 口径保真：让降级"可见"，而不是悄悄变保守
- **问题**：`initTokenEngine()` 失败只有 `console.warn`（`token-budget.ts:29`）。降级后**全部预算按高估口径判定**：实测中文样本启发式 6059 vs tiktoken 3612（≈1.68×）→ 历史预算提前约 40% 触发压缩、base 由 2150 膨胀到 ≈6.2k（7500 余量只剩几百 token → 降级链可能丢掉 M1/M2）。方向是"更保守"，所以不会崩，只会**静默损失质量**。
- **改法**：① 启动失败 → `renderLog('warn', …)` + 上下文明细面板增加一行"token 估算降级（启发式）"标记；② 在 `estimateTokens` 文档注释里写明"降级 = 全预算口径变保守"的语义（不做数值补偿，避免两套口径漂移）；③ **不写边界测试**（理由见 §1.2）。
- **验收**：mock 掉 `gpt-tokenizer` 后启动 → 日志有告警、面板有标记；正常加载时**逐字无变化**。
- **测试**：沿用 `token-budget.encoder.test.ts` 的 `vi.mock('gpt-tokenizer')` 范式，补"加载失败 → 状态可见"用例。
- **代价**：≈10 行 + 1 个 i18n 键（三语）。

#### S2 任务状态不参与压缩（与 W2 同一机制，双轨收益）
- **问题**：正在进行的任务（用户原始请求 + 未完成子任务）会被压进摘要，而摘要注入上限只有 300 tokens 且是"事实/指令/任务/决策"四节均分。对多步任务是硬损失。
- **改法**：在 system 尾部（语言指令**之前**）新增**当前任务段**（≤120 tokens，每轮重建、不进历史、不参与压缩）：
  - 来源一：本轮用户消息的意图/首句（已有 `detectWritingIntent` 的解析结果，零额外成本）；
  - 来源二：最近的**未完成**回执（复用 `extractSideEffectReceipts`，只取 `outcome='failed'` 或本轮开始后的写操作）；
  - 明确标注"（本轮任务锚点，非历史）"以免模型误当用户新输入。
- **验收**：把历史压过 2 批后，system 里仍能看到原始请求要点；`/clear` 后清空；未开始任务时零注入。
- **测试**：纯函数（消息+回执 → 任务段）+ 集成（压缩后仍在、`/clear` 后不在）。
- **代价**：+≤120 tokens/轮，含在 7500 预算内。

#### S3 工具契约的"全量档"与增长护栏
- **现状**：P0-3 已让 26 工具契约（3612）完整可读；`min(900+150N, 4000)` 在 **≈29 工具**时会重新截断。
- **改法**：① 保留并强化护栏用例（工具数增长 → 红，提示重估）；② 对**长窗口档**提供"工具契约不截断"开关（预算随窗口放大，强模型不需要为省 token 牺牲契约）。
- **验收**：29 工具时护栏红；长窗口档下 `truncated=false`。
- **代价**：小（配置项 + 测试）。

#### S4（评估项）强模型的"少即是多"精简档
长窗口强模型可考虑**降低**注入量（L1 编辑器段、记忆目录段按需），把上下文预算全留给正文与历史。**先评估不改**——需要 §4 的对照数据支撑（否则是凭感觉调提示词）。

### 轨道 W（抬高弱模型下限）

#### W1 按模型/档位的上下文策略（**本计划核心**）
- **问题**：所有预算都是全局常量（`compaction-prefs.budgetPercent` 默认 80、`computeMessageBudget` 窗口×80% clamp[16k,64k]、工具 `min(900+150N,4000)`、M1 300、L1 600）——同一个模型跑得怎样，与"用户给它配了什么角色"无关。
- **改法**：新增 `src/services/agent/context-policy.ts`：
  ```ts
  resolveContextPolicy({ contextWindow, tier }): {
    historyPercent: number        // 历史预算百分比
    historyCeilingTokens: number  // ⚠️ 必须一起给：绝对上限（见下）
    toolBudgetMode: 'full' | 'full-lite'
    m1BudgetTokens: number        // 会话摘要注入上限（须与生成端长度指令同步，见下）
    l1BudgetTokens: number        // 编辑器段上限
    taskAnchor: boolean           // §S2/W2 任务锚点是否启用
  }
  ```
  - **强档**（`elite` 或窗口 ≥ 200k）：`historyPercent 90` + **`historyCeilingTokens` 96k–128k**、`full`、M1 **400**、L1 600、taskAnchor ✔（多步任务同样受益）
  - **标准档**（`standard` / ≥ 64k）：**与现状逐字一致**（80 / 64k 上限 / full / 300 / 600）
  - **弱档**（`budget` 或窗口 < 64k）：`historyPercent 60`（更早压、上下文更干净）、`full-lite`、M1 **200**（更短、更结构化）、L1 300、taskAnchor ✔✔（弱模型最需要）
  - **优先级**：**用户显式配置 > 策略缺省**（与 `resolveCompactionPrefs` 的"只影响之后的压缩"语义一致）；档位来源：Agent 面板用 `agentModeToTier(mode)`（`model-router.ts:96`），工作流用 `purpose → tier`（`PURPOSE_TIER_MAP`，`model-router.ts:44`）。

  > ⚠️ **两个必须一起改的点（否则"90%"是空动作）**：
  > 1. **绝对上限**：`computeHistoryBudget` 现在是 `clamp(窗口×%, 1000, 64000)`（`compaction-prefs.ts:65`），消息预算上限同样是 64k（`agent-engine.ts` 的 `MAX_MESSAGE_BUDGET_TOKENS`）。200k 窗口算 90% = 180k → **被 64k 天花板吃掉**。故策略必须同时给上限；放宽上限的代价是**单次请求成本上升**，收益是压缩次数与信息损失下降——这是本计划里最需要用 §4 数据裁决的一处。
  > 2. **摘要的"生成上限"与"注入上限"必须同源**：生成端的长度约束写在 `ccr.summaryPrompt` 文案里（当前"不超过 250 tokens"，`locale-data/agent.ts`），注入端是 `SESSION_SUMMARY_BUDGET_TOKENS = 300`（`context-builder.ts:118`）。只调注入端会出现"给了 400 额度、摘要仍按 250 生成"的死额度；故 `m1BudgetTokens` 要同时驱动**文案里的数字**与**注入端截断值**（文案参数化，别再硬编码 250）。
  - **工具档的取舍**：弱档**不减少工具**（弱模型看不见的工具 = 不可调用，这是 P0-3 签名补偿的教训），而是 `full-lite` = 意图相关工具给完整 prose、其余只给"名字 + 签名"（仍可调用，省下的额度还给上下文）。
- **验收**：同一会话切换模型/档位 → 面板显示的 base/history 预算随策略变化；用户手动改过 `compaction` 的值时**策略不覆盖**（有测试锁定）。
- **测试**：纯函数矩阵（3 档 × 窗口边界 16k/64k/200k）+ store 集成（策略进入 `AgentEngineOptions` 与装配路径）+ 优先级用例。
- **代价**：中（新模块 + 3 处接入点），但**这是唯一能把两条轨道同时推进的结构性改动**。

#### W2 任务锚点（同 S2，弱模型收益更大）
见 §3 S2。对弱档默认开，且 M1 更短（W1）→ "任务锚点 + 短摘要"组合正是弱模型需要的形态。

#### W3 记忆自动召回（弱模型不会主动 @）
- **现状**：`@文件名` 硬门控（`matchMentionedManuals`，`memory-layers.ts:156`）+ `read_memory` 工具；弱模型既不会 @，也很少主动查。
- **改法**：对本轮用户消息做**零成本关键词命中**（复用现有 `scoreMemoryEntry`，`memory-layers.ts:175`），命中且该条为 `manual` 时自动注入 ≤400 tokens 正文（带「（自动召回）」标注）。不改 @ 行为；未命中零变化。
- **验收**：命中才注入、有标注、可用设置关闭；未命中路径逐字不变。
- **代价**：小（纯函数 + 1 个注入点）。

#### W4 弱模型的"未完成自检"（防过早收尾）
- **现状**：`MAX_TOOL_ROUNDS=8`、空结果占位、解析诊断回喂都有；但模型"自认为完成"时没有任何提示。
- **改法**：**仅弱档默认开**，且**每会话至多一次**：当本轮无工具调用、且用户请求含多步特征（意图为写稿/修稿，或文本含"然后/再/接着/顺便"）→ 注入一次 meta：「若仍有未完成步骤请继续；若已完成请列出完成清单」。幂等、可关闭。
- **验收**：只注入一次；第二次不再注入；强档不注入。
- **代价**：小；风险（可能与"直接回答"冲突）由"仅弱档 + 一次性"控制。

### 共同轨道

#### C1 集成层"阈值逐字等于用户值"断言
- **性质**：纯回归保险（今天零影响）。防的是将来有人把学习倍率无条件乘上去——那会让**关闭状态下**用户的 `minimumChangeTokens` 被静默缩放（过小 → 压缩激进丢信息；过大 → 不压 → 硬截断丢消息）。
- **改法**：`agent-store.test.ts` 补一条：关闭学习时，构造覆盖边界值的 `minimumChangeTokens`，断言压缩判定与用户值一致。
- **代价**：一条断言。

## 4. 度量：先立尺子，再动提示词

**没有对照数据的上下文改动一律不算完成**（否则就是"凭感觉调提示词"）。

**离线用例集**（新建 `docs/superpowers/specs/2026-10-15-context-quality-eval.md`，10–15 个上下文敏感场景）：
1. **跨轮事实保持**：第 3 轮确认的设定，第 12 轮（历史已被压过 2 批）仍被正确引用；
2. **工具契约完整性**：把工具集撑到截断线以上 → 被截断工具能否被正确调用（当前有签名补偿，需验证是否真的够用）；
3. **长任务不跑偏**：多步任务在第 N 轮后仍完成剩余步骤（W2 的主指标）；
4. **摘要保真**：批内关键实体（角色名/章节号/写入目标）在摘要中的保留率（已有 `ccr-fidelity` 可直接产出数字）。

**在线指标**（已具备，无需新建）：`llm_calls`（prompt/cached tokens、`prefix_fingerprint`）、学习引擎统计（压缩/跳过/截断/保真告警）、保真缺失类别分布。

**双轨验收口径**：

| 轨道 | 主指标 | 不许发生的 |
|---|---|---|
| S | 跨轮事实保持率、工具调用成功率（与关闭本机制时对照） | 任何一项因上下文层下降 |
| W | 首轮工具调用正确率、任务完成轮数、过早收尾率 | 弱档指标不得低于改动前 |

**执行方式**：可复用既有互评资产（`mutual-evaluation-workflow`：spawn-reviewers → synthesize-scores，落 `evaluation_scores`），也可先人工跑 10 例建立基线。

## 6. 与已完成工作的关系

- **已完成（附录 B，已推送）**：观测面闭环（实发口径/前缀）、压缩统计与保真、`version` 校验、重生成反馈、回执跨语言——这些是**本计划的前置**：没有可信的观测，§4 的双轨口径就无从对照。

## 7. 风险清单

| 风险 | 应对 |
|---|---|
| 策略层与用户偏好冲突（用户改了值却被策略覆盖） | 优先级写死为"用户显式值 > 策略缺省"，并有专门用例 |
| 任务锚点挤占预算或与用户输入混淆 | 硬上限 120 tokens + "非历史"标注 + `/clear` 清空 + 测试锁定 |
| 弱档"更早压缩"反而丢掉细节 | 与 W2 任务锚点同批上线（锚点保住任务状态，摘要只需管事实）；用 §4 用例 3 对照 |
| 自动召回误注入无关记忆 | 阈值对齐 `scoreMemoryEntry` 现有分档，仅 `manual` 条目，≤400 tokens，可关闭 |
| 未完成自检把简单请求变啰嗦 | 仅弱档 + 每会话至多一次 + 可关闭 |
| 度量缺基线导致"改了但说不清好坏" | 批 1 起同步落 §4 用例集，先测基线再改 |
