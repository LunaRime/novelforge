## 一、来源

本文件评估一份外部提出的 i18n 重构方案，其主张为
**「语言优先 + 模块分层 + as const 类型 + 动态导入 + CI 护栏」**：

```
src/i18n/
├── index.ts / types.ts / config.ts / useTexts.ts
├── zh-CN/{common,editor,character,blueprint,agent,settings,memory,errors}.ts
├── en-US/（同上）
└── ru-RU/（同上）
```

方案原文的迁移清单与收益声明：

| 方案声明 | 原文 |
|---|---|
| 调用方 | 「对外接口保持不变」「调用方零改动」 |
| 收益 | 「首屏翻译体积减少 70%」 |
| 类型 | 「key 拼错在编译期就能发现」（视为待新增能力） |
| 命名空间 | 8 个（common/editor/character/blueprint/agent/settings/memory/errors） |
| 结构 | 单文件不超过 300 行；加新语言只需复制一个文件夹 |

## 三、逐条核验

### ✅ 类型保护 —— **已具备，属伪需求**

`TextKey` 早已是 `keyof typeof UI_TEXTS_DATA`，拼错 key 现在就是编译错误
（3502 个调用点全部受此保护）。方案把它列为待新增能力，前提不成立。

⚠️ **但拆分时会得而复失**——见 §四.3。

### ⚠️ 「调用方零改动」—— **不成立**

方案导出的 `UI_TEXTS_DATA` 是**嵌套形状**：

```ts
UI_TEXTS_DATA['zh-CN'].editor.save    // 方案
UI_TEXTS['editor.save']               // 现状（返回 {zh-CN, en-US, ru-RU}）
```

两者不是同一接口。要做到零改动，新结构必须在出口处**重建出旧形状** —— 方案的
`index.ts` 没有这一步。

### ⚠️ 模块分层 —— **方向对，但「8 个命名空间」是错的**

第一段前缀有 **119 种**且极不均：`log` 一族单独 448 key。
按方案的 8 个命名空间切，`log` 会被塞进 `common` 或 `agent`，单文件必然远超方案自称的
300 行上限 —— **方案违反自己的规则**。

正确做法是按**实测分布**定切分点（多个小前缀合成一份，`log`/`tool`/`prompt` 单独成份）。

### ❌ 动态加载（`useTexts`）—— **本仓不适用**

三条独立理由，任一条都足以否决：

1. **主进程用不了**：`electron/` 有 376 处同步 `t()`，React hook 触不到
2. **服务层/工作流用不了**：纯函数层同样大量同步调用，且 `t()` 目前无异步形态
3. **Electron 不是 Web**：字典已在本地 bundle 内，动态 `import()` 省的是**解析/求值**
   时间，不是网络下载。方案「首屏体积减少 70%」是**网页论证**，此处不成立

且引入 hook 后，数百个消费组件都要补加载态（`if (!texts) return <Skeleton/>`），
改动面与 §二 的 3502 个调用点同量级。

### ✅ 语言优先布局 —— **可采用，但理由需补充**

方案的理由（加新语言只需复制一个文件夹）成立。但要补两个前提：

- **本仓更常发生的是「加 key」而非「加语言」**：key 优先下加一个 key 只动一行（三语并排），
  语言优先下要动 3 个文件。当前的 key 优先布局对**日常操作**更优。
- 加语言那一次性操作，本可由 codemod 生成整列，不必为它牺牲日常体验。

→ 语言优先**不是错的**，但它是**为一次性事件优化日常体验**的取舍，需明确知道代价。

### ✅ CI 护栏 —— **应当做，且独立于其他改造**

与会话中新建的 `src/shared/i18n-key-guard.test.ts` 互补：前者管「引用了不存在的 key」，
护栏管「文件结构不再膨胀」。

## 四、三个可选路径

### 路径 A（推荐）：拆文件，不换形状

把 `locale-data.ts` 按前缀切成多份，**每份仍是 `'key': {zh,en,ru}` 条目**，index 合并回
同一个扁平对象。

```
src/shared/locale-data/
├── index.ts        # 合并 + 导出 UI_TEXTS_DATA（形状与今天完全一致）
├── log.ts          # 448 key
├── tool.ts         # 217
├── prompt.ts       # 169
├── agent.ts        # agent + tip + … 合到 ~300
└── …
```

| | 结果 |
|---|---|
| 3502 个调用点 | **零改动** ✅ |
| `TextKey` 类型 | **零改动**（`keyof` 合并对象仍出字面量）✅ |
| `t()` 签名 | **零改动**（同步、扁平 key）✅ |
| 主进程 376 处 | **零改动** ✅ |
| 单文件行数 | 3485 → 全部 < 500（`log` 一族是三语同行，448 行）✅ |
| 加新语言 | 仍要每 key 加一列（**代价不变**，见 §三 语言优先） |

**这是唯一一个「收益明确、风险接近零」的路径。**

### 路径 B：语言优先 + 合并层

在路径 A 基础上改成语言优先布局，出口重建旧形状：

```ts
// 类型：从各模块直接取字面量（不能走 Object.fromEntries，否则类型退化）
type Keys = keyof typeof zhCN & keyof typeof enUS & keyof typeof ruRU
export type TextKey = Keys
// 运行时：按 key 重建 {zh,en,ru} 三语对象，再断言为 Record<TextKey, …>
```

| | 结果 |
|---|---|
| 调用方 | 零改动（前提是合并层写对）⚠️ |
| 加新语言 | 复制一个文件夹 ✅ |
| 翻译对齐可见性 | 变差（要跨文件比）⚠️ |
| 类型安全 | 需手工保证传递，写错就静默退化成 `string` ⚠️ |

### 路径 C：完整方案（含动态加载）

**不建议**，理由见 §三（动态加载三条否决理由）。

**步骤 2 的验收标准要写死**：合并后的 `UI_TEXTS_DATA` 必须与改造前**逐字节等价**
（写一条临时脚本对拍 `JSON.stringify`）。这是路径 A「零行为变化」的唯一硬证据。

⚠️ **对拍取 key 集必须用 `import` / `Object.keys`，不能用正则扫源码**。2026-09-25 实测：
本仓字典有**两种条目写法**（3285 条值同行 + **2 条值换行**，如 `tool.listOutlineDesc`），

| 正则 | 漏读场景 | 实测计数 |
|---|---|---|
| `^\s{2}'key':\s*\{`（行首锚定） | 两条目挤在同一行时漏第二个 | **3287** ✅ |
| `'key':\s*\{\s*'zh-CN'`（值形状锚定） | 多行条目全漏 | **3285** ❌ 少 2 |

即：**看起来更具体的值形状锚定反而漏 2 条**，行首锚定只要求前导缩进、不关心值在第几行。
用错方法会让"逐字节等价"的对拍给出假绿。

⚠️ 护栏脚本要自己先做一次「故意失败」验证 —— 否则它可能从未真正生效
（本会话已四次遇到「审计/清单与实况不符」）。

## 六、明确不做的部分

| 项 | 理由 |
|---|---|
| `useTexts` 动态加载 | 主进程 376 处 + 服务层同步调用用不了；Electron 无网络下载收益 |
| 8 个固定命名空间 | 与实测的 119 前缀不符，会给 `log`(448) 等造出超大文件 |
| 「调用方零改动」的说法 | 形状变了就必须改，除非出口重建旧形状（路径 B） |
| 把 `t()` 改成异步 | 3502 个调用点 + 主进程 |

### 与本文原口径的两处偏差（据实修正）

1. **「`JSON.stringify` 逐字节等价」改为「按 key 排序后逐字节等价 + key 集完全相同」**：
   条目按前缀分片后，合并对象的**枚举顺序必然变**，原样比对做不到。排序口径**更强**
   （逐一核对每个 key 的三语值），且已验证无消费方依赖顺序。
   ⚠️ 取 key 集必须用 `import` / `Object.keys`——正则扫源码会给**假绿**（见 §五 的两种正则盲区）。
2. **对拍工具用 `esbuild` bundle 而非 `tsx`/`vite-node`**（本仓无后者）：
   `npx esbuild <入口> --format=cjs --bundle --outfile=<临时>` → `require` 后哈希。

- 护栏阈值（≤600 行 / ≤550 条）刻意留了余量：职责是拦**重新膨胀**，不是逼人给每条新增 key 重新分片。
  真撞上限时**应拆新分片，不要调高阈值**。
- ✅ **三语各切一遍界面已真机确认（2026-09-25，用户实测无问题）** —— 至此 §五 的 6 个阶段全部闭环。
